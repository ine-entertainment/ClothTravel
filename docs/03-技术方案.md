## 1. 技术目标

1. **支持多端**：微信小程序（MVP）、商家 H5、运营后台；后续 App（Flutter）。
2. **交易可靠**：支付、押金、退款、分账、订单状态可追踪、可对账。
3. **库存不超卖**：一物一码 + 按日锁档 + 事务 + 幂等。
4. **履约可运营**：发货、物流、归还、质检、理赔全链路留痕。
5. **快速上线**：MVP 采用模块化单体，不做过度微服务化。
6. **可扩展**：多城市、多商家、多门店、摄影/化妆/社区逐步接入。

                            │

### 2.1 为什么先用模块化单体

- MVP 团队小、订单量低，微服务会增加部署、联调、排障成本；
- 模块边界按领域划清（用户/商品/库存/订单/支付/履约），后续可拆分；
- 先保证事务一致性（订单+库存+押金），比“架构先进”更重要；
- 当日订单量到 1 万+ 或团队 > 15 人，再按库存、支付、内容拆服务。

## 5. 核心数据模型

> 金额统一用 `DECIMAL(10,2)`，时间用 `DATETIME`，所有表带 `created_at/updated_at/deleted_at`。敏感字段加密存储。

### 5.1 用户与地址

### 5.2 商品与库存

```sql
product_spu (
  id BIGINT PK,
  merchant_id BIGINT,
  city_id BIGINT,
  title VARCHAR(128),
  category VARCHAR(32),        -- 连衣裙/汉服/民族服/配饰
  style_tags JSON,             -- ["海岛","法式","白色"]
  scene_tags JSON,             -- ["海边","古城","街拍"]
  description TEXT,
  deposit_amount DECIMAL(10,2),
  rent_price_3d DECIMAL(10,2),
  rent_price_5d DECIMAL(10,2),
  rent_price_7d DECIMAL(10,2),
  cleaning_note TEXT,
  status TINYINT,              -- 草稿/上架/下架/审核中
  INDEX(city_id, status),
  INDEX(merchant_id)

  id BIGINT PK,
  spu_id BIGINT,
  size VARCHAR(16),            -- S/M/L/XL
  color VARCHAR(32),
  market_price DECIMAL(10,2),
  deposit_amount DECIMAL(10,2),
  status TINYINT,
  UNIQUE(spu_id, size, color)
)

inventory_unit (
  id BIGINT PK,
  sku_id BIGINT,
  unit_code VARCHAR(64) UNIQUE, -- 一物一码
  condition_level TINYINT,      -- 新/良好/一般/维修
  status TINYINT,               -- 在库/已租/清洗/维修/丢失/退役
  current_city_id BIGINT,
  purchase_price DECIMAL(10,2),
  residual_value DECIMAL(10,2),
  last_cleaned_at DATETIME,
  INDEX(sku_id, status)
)

inventory_calendar (
  id BIGINT PK,
  unit_id BIGINT,
  calendar_date DATE,
  status TINYINT,               -- 可租/锁定/已租/缓冲/不可用
  order_id BIGINT NULL,
  UNIQUE(unit_id, calendar_date),
  INDEX(order_id),
  INDEX(calendar_date, status)
)
```

> **按日一行**的日历表是 MVP 最稳的防超卖方案：下单时在事务里批量插入/更新所选日期的行，`UNIQUE(unit_id, calendar_date)` 保证同一件衣服同一天不会被两单占用。跨城/长租也能精确控制。

## 7. 关键技术难点与方案

### 7.1 库存防超卖

```text
用户提交订单
  → 校验 sku/尺码/日期
  → 查 inventory_calendar 可租实物件
  → Redis 锁 unit_id（可选，DB 唯一约束兜底）
  → 事务：插入订单 + 批量更新 calendar 为“锁定” + 写订单项
  → 支付超时/取消：释放 calendar
  → 支付成功：calendar 改为“已租”
```

- 用 `UNIQUE(unit_id, calendar_date)` 兜底，重复插入直接失败；
- 锁粒度按 `unit_id`，不要锁整个 SKU；
- 释放库存用延迟消息/定时任务，必须幂等；
- 大促/节假日提前压测，限制单用户并发下单。

### 7.2 支付与押金

- 微信支付 v3，回调验签 + 幂等（`out_trade_no` 唯一）；
- 租金和押金建议**两笔支付**或一笔支付后内部分账，账目更清晰；
- 押金冻结：微信支付分/预授权/支付机构冻结，按合作方式选；
- 退款走原路，部分退款记录明细；
- 每日对账：支付流水 vs 订单 vs 退款，差异告警；
- 分账：微信分账 API，先冻结再分账，售后可回退。

### 7.3 订单状态机

- 每个订单类型定义状态枚举 + 允许的迁移；
- 所有状态变更走统一 `OrderStateMachine`，记录 `order_status_log`；
- 定时任务扫描超时（未支付、未发货、未归还、未质检）；
- 状态变更后发消息（订阅消息/IM/短信），失败重试。

### 7.4 物流与归还

- 快递100 订阅轨迹，回调更新 `shipment`；
- 同城配送对接顺丰同城/闪送，取件码；
- 酒店代收：记录前台联系人/电话，签收凭证；
- 归还提醒：到期前 24h、逾期当天、逾期 3 天；
- 丢件：按物流保价/平台规则赔付。

### 7.5 图片/视频

- 客户端直传 OSS（后端签名），避免打爆 API；
- 图片实时裁剪/WebP/水印；视频转码 + 封面；
- 审核：先机审，敏感图转人审；
- 客片/质检照片保留原图，设置访问权限和有效期。

### 7.6 搜索

- 商品：标题、风格、场景、颜色、尺码、城市；
- 摄影师：风格、城市、价格、评分；
- 内容：标题、正文、话题、城市；
- MVP 可用 MySQL `LIKE` + 标签筛选，商品 > 2,000 后上 ES；
- 搜索词落库，做热搜和供给缺口分析。

### 7.7 消息与 IM

- 站内信/订阅消息/短信三通道，按优先级降级；
- IM 用腾讯云 IM，后端只做账号映射和敏感词；
- 禁止站外导流：图片 OCR/文本正则/人工抽检；
- 消息模板统一管理，支持多语言（后续）。

## 8. 安全与合规

| 项 | 措施 |
| --- | --- |
| 传输 | 全站 HTTPS，HSTS，证书自动续期 |
| 认证 | 微信 code 换 session；JWT/自定义 token；商家/后台独立账号体系 |
| 授权 | RBAC；商家数据隔离（merchant_id）；后台最小权限 |
| 敏感数据 | 身份证/实名信息 AES-256 加密；手机号脱敏；身材数据默认私密 |
| 支付 | 验签、金额校验、幂等、防重放；密钥 KMS/环境变量 |
| 接口 | 限流、防刷、参数校验、SQL 注入/XSS/CSRF 防护 |
| 文件 | 类型/大小校验、病毒扫描、图片鉴黄 |
| 审计 | 后台操作日志、订单状态日志、退款/押金审批日志 |
| 隐私 | 隐私政策、单独同意、最小化收集、注销/导出、留存期限 |
| 备份 | MySQL 每日全量 + binlog；OSS 版本；定期恢复演练 |
| 监控 | 错误率、P95、支付成功率、库存冲突、订单超时告警 |

## 9. 部署与环境

### 9.1 MVP 部署（单机/双机）

```text
阿里云/腾讯云
├── SLB / Nginx（HTTPS、WAF）
├── 应用服务器 2 台（Docker Compose）
│   ├── api
│   ├── admin-api
│   ├── worker（定时任务/消息）
│   └── nginx
├── MySQL 8（主从/云 RDS）
├── Redis 7（云 Redis）
├── Elasticsearch（可选，MVP 可后置）
├── OSS + CDN
└── 日志/监控（Loki/Prometheus/Grafana/Sentry）
```

- 环境：dev / test / prod 三套；
- CI/CD：GitHub Actions/GitLab CI，构建镜像 → 测试 → 部署；
- 数据库迁移：Flyway/Liquibase；
- 配置：环境变量 + 配置中心（后期）；
- 灰度：按城市/用户白名单。

## 12. 技术风险

| 风险 | 应对 |
| --- | --- |
| 库存超卖 | 日历表唯一约束 + 事务 + 压测 |

| 社区内容风险 | 机审+人审、举报、黑名单 |
| 单城模型未跑通 | 先手工履约验证，再加大研发 |
| 团队小、需求膨胀 | 严格 MVP 边界，双周评审砍需求 |
